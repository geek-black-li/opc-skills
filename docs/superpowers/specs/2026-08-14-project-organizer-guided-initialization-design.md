# ZX Project Organizer 引导式项目初始化与整理设计

## 目标

将 `zx-project-organizer` 从“根据已知事实生成目录提案”扩展为完整的引导式项目创建与存量项目整理 Skill。Skill 必须主动帮助用户补齐项目事实、推荐命名和结构，但任何推荐都不能自动成为已确认事实；目录、代码骨架、迁移和 Git 操作仍须绑定提案并经用户明确确认。

## 两条工作流

### 全新项目

Skill 识别空工作区或接受用户显式选择后，按需逐问逐答：

1. 项目用途、目标用户、核心能力和阶段。
2. 中文名称与英文项目标识；Skill 可推荐 `ai-huoke` 等小写横杠名称，但必须由用户确认。
3. 所需文档域和结构方案。
4. 是否存在前端，逐个确认终端、职责、技术栈和应用名称。
5. 是否存在后端，确认单体或多应用、职责、运行时和应用名称。
6. 逐应用询问是否生成可运行代码骨架；只为明确选择的应用生成。
7. 仅在需要代码骨架时继续询问框架、版本、包管理器、模块名、启动命令、端口和测试方式。
8. 询问已确认需要的数据库、缓存、消息队列、定时任务和 Git 初始化。
9. 汇总事实、推荐采纳情况、目录树、文件、代码骨架、命令、风险和未确认项。
10. 只有用户确认与当前规范化提案完全匹配的 `proposal_id` 后才写入。

### 存量项目

Skill 先执行只读审计，扫描目录、技术栈、入口、构建方式、Git 状态、现有文档、部署配置和路径引用，并把事实登记为 `confirmed`、`inferred`、`unknown` 或 `proposed`。随后逐项确认保留、移动、改名、新增和丢弃内容。

已有应用不得重新生成代码骨架。只有用户明确新增的应用可以进入骨架询问。所有移动和重命名必须先给出迁移映射、受影响引用、执行顺序、验证方法和回滚方式；没有完整确认时只能返回迁移提案。

## 引导交互契约

问题按依赖关系一次提出一个。每个关键问题包含：问题 ID、问题、为什么询问、推荐选项、推荐理由、可选项、每项影响和自定义入口。

推荐项只进入 `proposed` 状态。用户必须逐项接受、修改、拒绝或自定义；接受某一推荐不得连带确认其他问题。信息不足时推荐“补充事实”或“授权只读扫描”等安全澄清方式，不得返回无推荐或伪造业务依据。存量项目优先推荐沿用现有约定，破坏性操作优先推荐低风险方案。

## 应用边界与命名

前后端应用统一位于：

```text
development/frontend/apps/
development/backend/apps/
```

每个应用是独立可运行、测试、构建和交付的项目。不得创建 `services`、`packages`、`libs` 或 `shared-code`，应用之间不得直接引用源码，只通过 HTTP API、RPC 或消息协议协作。

前端应用使用 `<project-slug>-<terminal>`：

```text
ai-huoke-web-admin
ai-huoke-h5
ai-huoke-wx-mini
ai-huoke-uniapp
ai-huoke-ios
ai-huoke-android
```

单一后端应用允许 `<project-slug>` 或 `<project-slug>-api`。多个后端应用推荐 `<project-slug>-<responsibility>`，例如 `ai-huoke-worker`、`ai-huoke-scheduler`。存量项目的裸项目名不得被自动重命名。

运行时不进入目录名。Go、Python 和 Node.js 项目可以同时位于 `backend/apps`。API、RPC 和消息规范跟随提供方应用，按需放入其 `specifications/http-api`、`specifications/rpc` 或 `specifications/messages`，不得创建中央共享源码目录。

## 代码骨架边界

是否生成代码骨架必须逐应用、一次一个地询问，不提供隐式默认值。未决定时 `generate=null`；用户拒绝时才记录 `generate=false` 并只创建确认过的目录和文档；用户接受时记录 `generate=true`，再收集足够的技术参数并将生成命令、完整文件内容、启动命令和测试方式纳入提案。

新项目可以生成已确认的前端、Go、Python 和 Node.js 最小可运行骨架。存量应用只允许审计和迁移，不覆盖、重建或静默升级。技术栈或关键版本未确认时，Skill 只能推荐或继续提问。

## 结构方案兼容

`zx-full-delivery` 保持完整文档域，并将 `development/frontend/apps` 与 `development/backend/apps` 作为稳定的应用容器。用户确认的应用目录是受约束的动态扩展，不允许借此添加任意未确认路径。

`adaptive` 只生成已确认的边界。`custom` 继续把用户提供的完整结构视为权威结构，不得静默重命名、移动、添加或遗漏路径。

## 安全与确认

提案哈希必须绑定工作流模式、项目事实、推荐决策、应用清单、结构方案、完整目录树、文件内容哈希、代码骨架命令、迁移映射和 Git 选择。应用阶段不得重新推导或生成新提案；任何提案 ID、规范化载荷或当前工作区事实不匹配都必须返回 `blocked`，且不得写入。

## 验收标准

- 新项目信息不完整时按顺序提出一个带推荐的问题，且不写文件。
- 推荐项未被用户接受时保持 `proposed`。
- 前后端应用使用稳定 `apps` 层，命名符合已确认规则。
- 不生成 `services`、`packages`、`libs` 或 `shared-code`。
- 接口规范跟随提供方应用。
- 代码骨架按应用选择，未选择的应用不生成。
- 存量应用不被重新生成，迁移未确认时不写入。
- `zx-full-delivery` 基础结构、Codex 入口、README、场景夹具和契约测试保持一致。
