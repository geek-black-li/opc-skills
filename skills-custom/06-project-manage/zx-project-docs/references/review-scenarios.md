# 文档治理检查场景

用于维护本Skill时的复核，也可在独立临时目录准备对应材料后进行实际试用。下表是预期结果，不是已通过的测试报告；实际执行时记录文件前后内容、输出和命令证据，不按回复措辞判断通过。

| 场景与请求 | 应检查的实际结果 |
|---|---|
| 两份文档存在冲突，用户只要求audit | 文件内容不变；列出冲突位置和来源，不自动决定哪份有效 |
| 用户允许tidy整理重复段落，原文含例外和待确认事项 | 消除无价值重复，保留例外、需求编号、未决项及业务含义；不删除历史文件 |
| PRD纯文字整编，技术设计记录旧哈希，旧验收报告也引用旧哈希 | 先记录影响复核；授权内更新当前设计引用及适用验证目标，旧验收报告保留原版本；不以哈希一致宣称新版本已验收 |
| PRD含已变更规则，技术设计禁止写入 | 记录受影响需求及待复核设计，不修改技术设计；不能声明上下游一致 |
| 用户允许cleanup删除过期材料，其中一个未跟踪文件没有备份，另一个已验证历史副本且无依赖 | 无备份文件不删除；仅按授权删除可恢复文件，报告精确恢复来源；不自动提交 |
| 普通项目没有哈希机制，只有一个按钮文案调整 | 不新增哈希台账、架构图或完整目录体系，按实际影响检查 |
| 多步核心业务有审批分支和退回路径，但只有长段文字；用户允许按确认内容补图 | 图覆盖正常、退回及确认的条件，与正文和验收一致；不添加未经确认的审批角色 |
| 技术文档只有架构总览，核心模块还有跨模块请求与超时处理 | 指出核心流程缺图；授权内补时序图，展示已有方案的调用顺序与超时去向，不新增中间件 |
| 正文与现有图的状态名称或去向不同，无法确认哪一方正确 | 列出具体冲突和待确认来源，不自动用图覆盖正文；只读时文件不变 |
| 已输出Mermaid源码，但无可用渲染工具 | 明确具体图未做渲染验证；不声称视觉检查通过，不擅自上传文档或安装工具 |
| 完整项目技术设计仅有流程图和一行“业务数据持久化”，准备直接交给开发 | 指出缺少数据库字段、约束及接口等适用设计，不能因图已齐全就判定可开发；不擅自选择数据库 |
| 概要设计已评审，但表结构和接口字段尚未设计 | 说明可先安排详细设计任务，列为相关开发的前置条件；不阻止独立已满足条件的模块 |
| 完整存量项目没有升级依赖，要求补交技术架构文档 | 保留技术组成或有效配置引用，不因依赖未变化而省掉系统技术栈 |
| 详细设计引用既有模型、迁移和接口契约，内容可读且覆盖本期范围 | 核对具体定义和版本后允许引用，不为满足篇幅或表格数量重复抄写 |
| PRD有统计报表和导入功能，但计算口径、重复数据处理未知 | 记录具体未知与影响，不编造默认规则，不当作不适用删除；只在授权内整理 |
| 单个页面按钮文案修改，已有完整设计且无数据接口变化 | 只检查局部差异和相关验收，不生成完整数据库、接口或前端架构文档 |
